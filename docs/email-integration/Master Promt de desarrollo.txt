## 3. PRINCIPIOS NO NEGOCIABLES

### 3.1 Backend-first

Android no descargará ni procesará buzones completos.

Laravel será responsable de:

- OAuth y callbacks.
- Cifrado y renovación de tokens.
- Gmail API y Microsoft Graph.
- Webhooks, Pub/Sub y sincronización incremental.
- MIME, adjuntos, OCR y clasificación.
- Detección de duplicados.
- Candidatos, feedback, auditoría, reintentos y retención.

Android será responsable de:

- Iniciar la autorización mediante navegador seguro.
- Mostrar cuentas conectadas y estados.
- Consultar candidatos paginados.
- Editar, confirmar, ignorar y marcar duplicados.
- Importar de forma idempotente el movimiento confirmado a Room.
- Funcionar sin conexión con los datos ya sincronizados.

### 3.2 Una identidad: Firebase Auth

No implementes otro registro de usuario con contraseña en Laravel.

- Android obtiene el Firebase ID token del usuario autenticado.
- Lo envía como `Authorization: Bearer <id-token>` únicamente por HTTPS.
- Laravel verifica firma, audiencia, emisor, expiración y revocación cuando aplique.
- Laravel vincula el `firebase_uid` a un usuario interno.
- Nunca confíes en un `user_id` enviado por Android.
- Policies y queries siempre se limitan al usuario autenticado.

Sanctum puede usarse internamente si aporta valor, pero no debe duplicar Firebase Auth.

### 3.3 Fuentes de verdad y confirmación

Durante el MVP:

- Laravel/MySQL es la fuente de verdad de cuentas de correo, mensajes, adjuntos, sincronizaciones, candidatos, reglas y feedback.
- Room continúa siendo la fuente local del libro financiero existente.
- No introduzcas Firestore para este módulo.

Laravel y Room no pueden participar en una única transacción ACID. Implementa una saga idempotente:

1. Android solicita confirmar un candidato con una `Idempotency-Key`.
2. Laravel bloquea el candidato, valida ownership y duplicados, guarda la corrección y crea una confirmación `pending_import` dentro de una transacción MySQL.
3. Laravel devuelve `confirmation_id` y un DTO financiero inmutable.
4. Android ejecuta una transacción Room que inserta el movimiento, actualiza el saldo y guarda `origin_type=email_candidate` + `origin_id=confirmation_id` con índice único.
5. Android envía ACK al backend.
6. Laravel cambia la confirmación a `imported`.
7. Si falla la red, cualquier paso se puede repetir sin crear duplicados.

No afirmes atomicidad entre MySQL y Room. Documenta y prueba la recuperación.

La sincronización financiera multidispositivo completa es un proyecto separado y requiere un ADR antes de cambiar esta decisión.

### 3.4 Secretos y tokens

- Client secrets, refresh tokens y access tokens viven solo en backend.
- Nunca compiles secretos de Gmail/Microsoft dentro del APK.
- Nunca envíes refresh tokens a Android.
- Cifra tokens con claves versionadas y estrategia de rotación.
- Nunca registres tokens, cuerpos completos, números de tarjeta o adjuntos sensibles.
- Los últimos cuatro dígitos son el máximo dato de tarjeta permitido.

### 3.5 Alcance incremental

No construyas Gmail, Outlook, OCR y machine learning al mismo tiempo.

Orden obligatorio:

1. Estabilización.
2. Backend y autenticación.
3. Gmail con sincronización manual y correos sin adjuntos.
4. Clasificación determinista y candidatos.
5. API y revisión Android.
6. Gmail incremental y Pub/Sub.
7. Microsoft Graph.
8. Adjuntos y OCR.
9. Aprendizaje y autoaprobación.

## 4. ALCANCE DEL MVP

El MVP de correo termina cuando un usuario autenticado puede:

1. Conectar una cuenta Gmail.
2. Autorizar `gmail.readonly` con state y PKCE.
3. Sincronizar manualmente los últimos 30 o 90 días.
4. Detectar correos financieros sin adjuntos.
5. Extraer comercio, monto, moneda, fecha, dirección y últimos cuatro dígitos cuando existan.
6. Crear candidatos con confianza y razones explicables.
7. Revisarlos de forma paginada en Android.
8. Editar, confirmar o ignorar.
9. Importar la confirmación a Room exactamente una vez.
10. Desconectar Gmail sin borrar movimientos importados.

Fuera del MVP inicial:

- Outlook/Microsoft Graph.
- Gmail Pub/Sub.
- PDF, imágenes, Tika y PaddleOCR.
- Autoaprobación.
- Machine learning.
- IMAP.
- Sincronización multidispositivo de todo el libro financiero.

No implementes elementos fuera del MVP hasta superar su puerta de calidad.

## 6. MODELO DE DATOS MÍNIMO

Usa UUID o ULID públicos. Nunca expongas IDs autoincrementales como mecanismo de seguridad.

Tablas del dominio:

- `users`: `firebase_uid` único y datos mínimos.
- `connected_email_accounts`: proveedor, correo, tokens cifrados, scopes, estado, cursor, expiraciones y errores sanitizados.
- `email_oauth_states`: state de un solo uso, PKCE, expiración y consumo.
- `email_messages`: IDs del proveedor, metadata, hash, texto normalizado sujeto a retención y estado.
- `email_attachments`: metadata, hash, almacenamiento privado y estado; crear cuando inicie la fase de adjuntos.
- `financial_transaction_candidates`: extracción, dirección, monto, moneda, confianza, duplicados, estado y referencia de confirmación.
- `email_candidate_confirmations`: idempotency key, estado `pending_import|imported|failed`, payload financiero y ACK.
- `email_classification_rules`: reglas globales y por usuario con prioridad.
- `email_processing_feedback`: correcciones del usuario.
- `email_sync_runs`: cursores, métricas, errores y correlation ID.
- `audit_logs`: acción, actor, recurso y metadata sanitizada.

Restricciones obligatorias:

- Único: cuenta + `provider_message_id`.
- Único: usuario + `idempotency_key`.
- Único: usuario + `confirmation_id` donde aplique.
- Índices por usuario, estado, fecha, proveedor y cursor.
- Foreign keys explícitas.
- Soft delete solo donde exista requisito de recuperación o auditoría.

Montos:

- Backend y Android intercambian `amount_minor: Long` y `currency: ISO-4217`.
- No usar `float` o `double` para dinero.
- Definir `currency_exponent`; DOP, USD y EUR usan 2.
- Fechas de API en UTC con ISO-8601; Android convierte para presentación.

## 8. CLASIFICACIÓN

Implementa por capas y conserva las razones:

1. Remitentes configurables.
2. Palabras y expresiones financieras en español e inglés.
3. Regex para monto, moneda, fecha, comercio, referencia y últimos cuatro dígitos.
4. Parsers Strategy por proveedor o formato.
5. Historial de correcciones del usuario.
6. Machine learning solamente con dataset versionado y métricas.

Monedas iniciales:

- `RD$`, `DOP`.
- `US$`, `USD`.
- `EUR`, `€`.

No asumas que el primer monto es el total. Distingue subtotal, impuestos, balance, propina, monto autorizado, reembolso y total.

Confianza inicial explicable de 0 a 1:

- `>= 0.90`: elegible para autoaprobación solo si el usuario la habilitó; desactivada por defecto.
- `0.70–0.89`: alta confianza.
- `0.40–0.69`: revisión requerida.
- `< 0.40`: no crear candidato visible salvo diagnóstico controlado.

La deduplicación financiera marca; no elimina automáticamente.

## 9. OAUTH Y SINCRONIZACIÓN

### 9.1 Gmail

- Scope mínimo: `gmail.readonly`.
- Authorization Code, state de un solo uso y PKCE.
- Callback e intercambio de código en backend.
- Sincronización inicial limitada, por defecto 30 días; configurable a 90.
- Sincronización manual antes de Pub/Sub.
- `historyId` y `watch` solo después del MVP manual.
- Renovar `watch` diariamente y antes de su expiración.
- Mantener sincronización de respaldo porque las notificaciones pueden perderse.
- Preparar verificación OAuth y política de privacidad antes de beta pública.

### 9.2 Microsoft

- Permiso delegado mínimo `Mail.Read`.
- Soportar cuentas Microsoft personales y organizacionales según configuración.
- Delta queries y `deltaLink`.
- Webhook con validación de `clientState`.
- Endpoint de lifecycle notifications.
- Renovar suscripciones con anticipación.
- Recuperar notificaciones perdidas y suscripciones eliminadas.

## 10. SEGURIDAD Y PRIVACIDAD

- HTTPS obligatorio fuera de desarrollo local.
- CORS restrictivo; la app móvil no depende de CORS para autenticación.
- Rate limits por usuario, IP, endpoint y proveedor.
- Policies en todos los recursos del usuario.
- Validar OAuth state, PKCE, expiración, replay y redirect URI exacta.
- Validar firma/identidad de Pub/Sub y `clientState` de Microsoft.
- Tokens cifrados con versión de clave.
- Adjuntos fuera del directorio público, MIME real, tamaño máximo y nombre generado.
- Nunca confiar en extensión o Content-Type enviado por cliente.
- Logs estructurados con `correlation_id` y redacción de PII.
- Retención configurable; eliminar texto y archivos cuando expire.
- Proporcionar desconexión y eliminación de datos de correo.
- No mostrar cuerpo completo del correo en Android por defecto.
- Notificaciones push sin montos ni comercios sensibles completos.

Revisar también Android:

- Reglas de backup/data extraction.
- `FLAG_SECURE` y privacidad existentes.
- No usar logging `BODY` con datos financieros.
- No incluir secrets en `BuildConfig`.
